Scenarios

A scenario is a JSON file that describes a whole simulation: the species, the historical population and the founders sampled from it, the QTL and chip loci, the traits, the breeding scheme, the number of time steps, the master seed and the number of replicates. It is the input of the bngsim command line and of the planned web service, and runs in Julia with run_scenario.

using BnGsim
s = read_scenario("examples/minimal.json")   # read and validate
df = run_scenario(s)                         # per-step summaries of every replicate

The smallest example, examples/minimal.json:

{
  "schema": "bngsim-scenario",
  "schema_version": 1,
  "name": "minimal",
  "seed": 2026,
  "steps": 3,
  "species": {"name": "toy", "chromosome": [20000000, 10000000], "M": 100000000},
  "founders": {"ne": 100, "nt": 500, "mr": 1.0, "nid": 50},
  "loci": {"qtl": {"nlc": 50, "maf": 0.01}},
  "traits": [{"name": "y", "h2": 0.3}],
  "scheme": {"noff": 50, "nsire": 5, "ndam": 20, "evaluation": "phenotype", "selection": "truncation"}
}

Schema

The keys, their defaults and their meaning are listed in the docstring of Scenario (schema "bngsim-scenario", version 1). They mirror the Julia API: the scheme object takes the keywords of Scheme, with ASCII names for the Unicode ones (lambda, kappa, delta_F), and a trait takes those of BnGStructs.Trait (h2, sigma_a, mu, sex, age, and da for the distribution of the QTL effects).

Validation

read_scenario and parse_scenario check the whole document before anything runs and throw a ScenarioError that lists every problem with its path, rather than the first one; validate_scenario returns the list. Unknown keys, repeated keys, values of the wrong type and out-of-range values are errors, never ignored or repaired. So are combinations: a :gblup scheme without chip loci, weights that do not match the traits, a correlation matrix that is not a positive definite correlation matrix, more founders than the last historical generation holds, or a scheme that Scheme itself refuses. For example, a scheme with a misspelt key and a negative seed:

using BnGsim
text = replace(read(joinpath(pkgdir(BnGsim), "examples", "minimal.json"), String),
    "\"seed\": 2026" => "\"seed\": -1", "\"nsire\"" => "\"nsires\"")
validate_scenario(text)
3-element Vector{String}:
 "seed: must be an integer in 0:2^64-1; got -1"
 "scheme.nsires: unknown key (exp" ⋯ 230 bytes ⋯ "s, retain, report_reliability)"
 "scheme.nsire: required"

The number of loci that pass the maf filters is only known once the founders are sampled; a panel larger than that fails then, with an ArgumentError.

Canonical form

A Scenario holds every value, with the defaults filled. scenario_json and write_scenario write it with every key present, so the file states the whole simulation; reading it back gives an equal scenario, and writing that gives the same text.

s = read_scenario(joinpath(pkgdir(BnGsim), "examples", "minimal.json"))
print(scenario_json(s))

Runs and reproducibility

run_replicate runs one replicate and returns its population and summary; run_scenario runs replicates 1:replicates and stacks their summaries with a column replicate. Every random draw comes from a SimKey of the scenario's seed: the historical population from replicate 0 when it is shared (founders.shared_history, the default), then for each replicate r the founders (Domain.FOUNDERS), the chip and QTL loci (Domain.GENOTYPING), the QTL effects (Domain.QTL) and the breeding loop. A replicate is therefore the same whether it runs alone or with others, and on any number of threads.

Limits of version 1

  • Founders come from a FisherWright historical population; a scenario takes no file paths (the service accepts no user paths, roadmap I9).
  • Traits are additive (as the breeding loop).
  • One scheme for the whole run.
  • Provenance is written by the command line with the outputs (roadmap I2), not by run_scenario.
